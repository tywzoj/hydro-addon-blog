# Blog Behavior Reference

## Evidence and Scope

This guide describes behavior visible in this addon's source, not a record of successful runtime tests. The initial reference is revision `d4be3cd`. Update this guide and the relevant regression coverage when behavior changes.

Use the [official Hydro references](development.md#official-hydro-references) to verify inherited handler behavior, privilege semantics, validators, and persistence guarantees against the version actually used. Do not turn an implementation limitation into an approved product requirement.

## Storage and Routes

- Blog documents use `SYSTEM_DOMAIN = "system"` and `TYPE_BLOG = 70`.
- Top-level comments use `TYPE_BLOG_COMMENT = 71`, with a type-70 parent ID;
  nested replies are embedded within their top-level comment. Both levels'
  per-user like statuses use type 71 with article and top-level parent linkage.
- Per-user view and star state use the existing document-status APIs.
- Blog admission uses the independent global blog role policy. Guest starts with no access but can be configured to read; mutations require an authenticated profile.
- Blog handlers bypass only Hydro's inherited domain-view permission check. Valid domain-prefixed blog URLs share the same data and policy; domain membership, roles and permissions are unchanged.

| Route | Purpose | Additional preparation or checks |
| --- | --- | --- |
| `/blog` | Home list. | Access and published-read permissions. |
| `/blog/:uid` | User list. | System-domain user lookup; filter readable published/draft entries before pagination. |
| `/blog/:uid/create` | Create form and submission. | Authenticated `CREATE` permission and URL user equal to the signed-in user, including root; published/pinned creation also checks its respective permission. |
| `/blog/:uid/:did` | Post detail, stars, paginated comments, replies, deletion, and likes. | Exact URL-author match and article readability; mutations require authentication and their explicit permission. |
| `/blog/:uid/:did/edit` | Edit form, update, delete, pin and publication operations. | Authentication, readability, and independent action-specific permissions. |
| `/blog/settings` | Global review settings and overview. | Access, authentication, `MANAGE_SETTINGS`, and sudo before displaying/saving the configuration form. |
| `/blog/settings/roles` | Role creation/deletion. | Management permission; GET and deletion require sudo, creation POST does not. |
| `/blog/settings/permissions` | Permission matrix. | Management permission and sudo. |
| `/blog/settings/users` | User-role assignment. | Management permission and sudo; only effective root/custom-role users are listed. |
| `/blog/review` | Global pending queue. | Authentication, access and independent `REVIEW`; does not require ordinary draft reading. |
| `/blog/review/:did` | Current pending content, reports and decisions. | `REVIEW`, pending state, and matching decision-generation/content-version tokens. |
| `/blog/review/:did/reset` | Minimal counter view and reset. | Independent `RESET_REVIEW_COUNTERS`, without general draft-content access. |
| `/blog/:uid/:did/report` | Article report or own accepted-receipt acknowledgement. | Exact author binding; new reports require authenticated non-author readability, publication, eligible version and enabled review. |

Source: [constants](../features/constants.ts), [route handlers](../features/handler.ts), and [base preparation](../features/handler.base.ts). Domain-prefixed URLs may be generated by Hydro; verify them in the target deployment rather than constructing them by assumption.

## Lists and Ordering

| Scenario | Draft filter | Default order | Pin precedence |
| --- | --- | --- | --- |
| Home, any admitted viewer | `draft: { $ne: true }`. | `firstPublishAt` descending. | None added by the home handler. |
| User list without applicable draft-read permission | Owner filter and `draft: { $ne: true }`; published-read permission required. | `firstPublishAt` descending. | `pin` descending before the selected key. |
| User list with applicable draft-read permission | Owner filter; drafts included. If published reading is denied, include drafts only. | `updateAt` descending. | `pin` descending before the selected key. |

Supported `sort` values are `latest`, `latest_update`, and `views`, mapped to descending `firstPublishAt`, `updateAt`, and `views`. An explicit supported selection overrides the default.

On user article lists, the Draft label precedes Pending review or Review required
when both labels are visible.

The home sidebar orders available actions as Create a Post, My Blog, Blog review,
and Blog settings. My Blog is shown to authenticated readers independently of
creation/review grants and targets the signed-in user. A user's blog sidebar
shows the owner's title and an authorized Create a Post button only; the three
home navigation buttons are omitted even for reviewers/managers. Creation still
requires the signed-in user's own list, including for root.
When review is disabled, review links are also omitted from the home sidebar,
native user dropdown and article action sidebar; report and reset-entry controls are
hidden. Direct authorized review/reset routes remain available for existing holds
and recovery. Settings access remains visible to authorized managers.

Handlers paginate ten posts at a time and validate the page as a positive integer. No additional equal-key tie breaker is explicitly specified in the handler sort objects; do not promise a particular tie order without verifying the query behavior.

Source: [list handlers and sort map](../features/handler.ts), [model queries and indexes](../features/model.ts).

## Article Detail Layout

The right sidebar shows the author profile first, followed by a separate,
permission-filtered Article actions section:
edit, publish/submit/withdraw, pin/unpin, delete, review and counter reset.
It is omitted when no action is available. Existing confirmation dialogs and
independent action permissions remain unchanged. All action buttons are text-only,
including Edit.

Review status, reviewer-visible report counts
and publication-blocking notices appear in the article footer alongside views,
stars and reporting. Only the author sees their latest nonempty review comment
in a separate section below the article, before discussion comments. Non-authors,
including reviewers and root, do not receive that feedback in ordinary article
responses. Empty feedback sections are omitted, and feedback remains escaped text.

Article detail never loads or exposes report comments, including for reviewers.
Reports remain on the authorized review detail page, with each entry explicitly
labeling its reporter through a native user link, alongside content version,
acceptance time and escaped comments. That page retains its existing pagination
and `REVIEW` gate; ownership and reset permission alone do not grant access.

Rejection counts are displayed only on authorized review queue/detail and counter
reset pages. Ordinary lists, article detail and editor responses omit
`rejectionCount` for everyone, including owners and reviewers, without changing
stored counters or publication-limit enforcement. Authors still see review status,
feedback and the publication-blocked notice.

The review detail heading appends the localized review type after a middle dot:
`Article title · Publication review` or `Article title · Report review`. There is
no separate review-type paragraph in the article body.

## Article IP Privacy

Article IP addresses are server-only metadata. Home/user lists, article detail,
editor, review queue and review detail responses omit the article `ip` and any
legacy embedded reply `ip` fields, for both HTML template data and JSON.
This applies equally to guests, authors, reviewers and root; permissions do not
grant an exception. Current independent comments already exclude both levels'
IP fields through their query projection.

The response-only `articleForResponse` projection clones the article and legacy
reply objects. It does not erase stored addresses, modify prepared documents,
remove review tokens or change authorization. Existing write-side IP capture and
server audit payloads remain unchanged. The separate `articleForReader` helper
still controls review-metadata visibility and is also used for audit snapshots;
user-facing article data must additionally pass through `articleForResponse`.
No database migration or framework serialization patch is required.

## Publication and Editing

- Article deletion, explicit publication/withdrawal, saving published content or
  changing its publication state, review approval/rejection, and counter reset
  require Hydro's native confirmation dialogs in the browser. Rejection opens an
  action dialog with optional review comments and the rejection consequence
  notice; cancellation preserves the draft comments without submitting.
  Approval uses a Yes/No confirmation with no comment input and submits empty
  comments, even after a cancelled rejection dialog. Declining preserves
  editor content and review comments and sends no mutation. Confirmation retains
  the selected submit button and hidden version fields, including keyboard
  submissions. Ordinary draft saves, pinning and stars do not add confirmation;
  reporting and comment deletion keep their existing native dialogs. These UI
  guards do not replace server authorization, validation or concurrency checks.
  Confirmation text is translated using the current request and passed through
  `UiContext`, so an older cached frontend language catalog cannot drop new
  translations. The native frontend catalog remains a compatibility fallback.
- New documents initialize `updateAt`, zero views, and zero replies.
- Creating a draft or pre-publication submission does not assign `firstPublishAt`;
  actual publication assigns it, including first approval.
- Every model edit refreshes `updateAt`. An edit explicitly publishing a document without `firstPublishAt` assigns the new update time as its first-publication time.
- An existing `firstPublishAt` is preserved by edits, including draft transitions and later republishing.
- `BlogModel.get` supplies `updateAt` as an in-memory fallback for a non-draft
  document without `firstPublishAt`. A later checked mutation preserves that
  value in storage before changing the timestamp or visibility; no bulk migration runs.
- List reads use `getMulti`, not the single-post fallback. Do not assume missing publication fields are backfilled or sorted as if persisted.
- The new-post form initially checks Draft. An omitted draft field defaults to draft on creation; the visible-checkbox marker makes an explicitly unchecked control publish instead.
- Updates preserve omitted draft/pin fields. Visible-checkbox markers distinguish unchecking a control from not supplying it.
- JSON `false` and numeric `0` are explicit false values, not omitted fields. Article Boolean parameters reuse Hydro conversion while preserving omission defaults.
- Independent publish, pin and star actions require an explicit state value. Missing, null or empty states are rejected before persistence; only content submissions support omitted draft/pin fields.
- Content edits that stay published require edit and publish permissions. Publishing, withdrawing, pinning, and deleting have independent controls and do not imply permission to edit content.
- Pending-withdrawal controls use an authorized flag derived from the original
  article, not the private-data projection. Delegated users with draft-read and
  unpublish permission can withdraw another author's pending draft without
  receiving its private review metadata or requiring publication permission.
- Article edits compare update timestamp, draft state, write revision, and empty
  pending-report slot before writing, advancing revisions/timestamps monotonically.
  Stale writes fail instead of overwriting newer publication/review state.
- All create/edit/publish request paths apply the global review mode and existing
  review hold. The review section below defines intentional publication changes.

Source: [model add, get, and edit](../features/model.ts), [form template](../templates/blog_edit.html), and [submission handlers](../features/handler.ts).

## Views and Stars

- Detail reads track views only when the requester has `PRIV_USER_PROFILE` and a positive user ID.
- If that user's stored status has no recorded view, the handler increments the count and records `view: true`, then updates the response document's count.
- A later sequential read with the recorded view does not increment again.
- The star operation validates a boolean and sets the requesting user's star status. Detail rendering uses that user's stored star state, defaulting to `false`.

The view increment and status write are separate operations. This source alone does not establish atomicity or exactly-once counting under simultaneous first views. Do not describe concurrency guarantees without implementation evidence and tests.

Source: [detail and star handlers](../features/handler.ts), [status helpers](../features/model.ts), and [detail template](../templates/blog_detail.html).

## Write-Side Safeguards

- Create and edit submissions use Hydro validators for title, content, draft, and pin inputs.
- Articles can only be created under the authenticated user's identity. Other users' lists have no create entry, and both create GET and POST reject a different URL user, even for root. Existing third-party edit and management permissions are unchanged.
- Creation invokes `limitRate("add_blog", 3600, 60)` before persistence. Verify the argument semantics in the applicable Hydro implementation rather than assuming a rate policy from these values alone.
- Create, edit, and delete paths record `blog.create`, `blog.edit`, and `blog.delete` operation logs.
- Deletion removes the document, its status records, all comment documents,
  embedded replies, both levels' like statuses, and independent report receipts.
- Article and settings mutations log after successful persistence; a failed required log is not reported as success. There is no transaction or rollback guarantee across persistence and audit writes.
- The legacy `BlogModel.addReply` helper delegates to independent comment storage;
  it no longer appends top-level replies to the article or updates its timestamp.

Preserve these validators, rate-limit calls, and audit calls when changing write paths. If a change intentionally alters them, state the intended behavior and add applicable verification.

Source: [write handlers](../features/handler.ts), [model deletion and reply helper](../features/model.ts).

## Global Roles and Settings

- The original 17 article/settings grants are documented in the
  [permission plan](plans/blog-permissions.md); the [comment plan](plans/blog-comments.md)
  adds four grants, and [article review](plans/blog-review.md) adds two, for
  23 matrix rows. Article creation has one `CREATE` grant;
  each article own/others pair remains strictly scoped. Comment deletion uses
  the separate native discussion branches below.
- Blog permissions apply to all users automatically. There is no blog membership, admission, join, leave, removal, or invitation state.
- `PRIV_EDIT_SYSTEM` forces root; otherwise an unauthenticated identity uses guest and an unassigned eligible user uses default. Explicit root assignments are supported; guest cannot be assigned to a user. Legacy guest assignments resolve to default for authenticated users without modifying their account or domain data.
- Root uses an immutable all-permissions mask. Fresh default grants reading,
  starring, own-article operations, comment/reply posting and likes, own-comment
  deletion, and own-article top-level moderation. Guest starts empty. Existing
  stored masks are not augmented on upgrade: administrators must enable new
  comment bits explicitly. Managers may configure guest masks, but mutations
  still require authentication.
- One `MANAGE_SETTINGS` permission governs the entire settings area. Built-in roles cannot be deleted; new roles copy the current default permissions.
- `blog.settings` stores one versioned global configuration. `blog.user` stores explicit assignments. Revision-checked configuration updates reject stale saves; unchecked matrix columns persist zero.
- Permission-matrix columns follow Hydro's configured-role dictionary order, then
  append missing built-ins in guest/default/root order. Root remains last.
  `permissionRoleOrder` records first configuration order without changing masks
  or assignments. A newly created role follows already configured roles, not an
  alphabetical sort. Numeric role names follow JavaScript dictionary enumeration,
  as in Hydro. Legacy settings without this metadata preserve custom-role order
  and append built-ins; earlier builtin-configuration history is not reconstructed.
- Custom role IDs are immutable. Deletion retires the ID and makes affected assignments resolve to default. Recreating the same name never reactivates old assignments; stale assignment records may remain as harmless references to retired IDs.
- The user table filters out effective guest/default users before counting/pagination, includes forced root and does not duplicate root entries. The native user selector can still assign a role to an unlisted user.
- The user-list query begins with indexed visible-role assignments, joins eligible profiles, unions forced-root users, and deduplicates before sorting, counting and pagination. It does not join every profile to role assignments. Only the returned page's full profiles are loaded; forced-root privilege filtering may still scan profiles.
- Role assignment adapts the native domain-user controls: header Assign User Roles dialog,
  multi-user selection, inline role dropdowns, checkbox selection, batch assignment,
  and resetting a role by selecting default. There is no remove-user action.
  Guest is excluded from every assignment control and rejected by both assignment APIs,
  while its anonymous-access permissions remain configurable in the matrix. Forced
  root rows are read-only; single-user assignment remains API-compatible.
- Both native user search and selected-user fetching use the system-domain API, so a delegated blog manager can assign users from a restricted domain without domain-view permission. Page navigation remains in the original domain.
- Role management uses a header creation dialog and confirmed batch deletion.
  Both batch APIs validate all selected targets before persistence; no
  cross-document transaction guarantee is added.
- Blog sudo verification uses the system-domain identity endpoint and returns to
  the original settings URL, so a restricted current domain cannot block
  reauthentication. Settings sidebars retain native styles and show the active page
  consistently with or without a domain prefix.
- Draft details, editor responses, JSON and stars check readability before view/status side effects. This intentionally closes the previous draft direct-link gap.
- Review/reset grants are appended without augmenting existing masks. There is
  no implicit article-owner bypass or domain-role mutation.
- The two review/reset entries form their own Blog review permission family,
  retaining the native family-table layout and existing permission bit values.

## Article Review and Reports

- Settings default to disabled review, report limit 3, rejection limit 3,
  reviewer reminders enabled, and a 1440-minute summary interval.
- Saving disabled mode requires a localized native warning and an explicit
  confirmation field on the server. After the revision-checked settings write,
  all currently pending articles are approved in bounded batches through the
  ordinary approval transition. This publishes/restores articles, clears counters,
  grants report-version immunity where appropriate, and emits author notices and
  per-article Oplog entries. Settings authority authorizes this automatic approval
  without granting general reviewer access.
  The queue cutoff is captured before committing settings, so a delayed audit
  cannot extend the sweep to submissions under a later review configuration.
- Concurrent completed decisions, withdrawals and deletions are not overridden.
  Stale pending edits are reloaded with bounded retries. Settings, approvals,
  audit and messages remain separate native writes: a failure is reported, not
  rolled back or called complete. A subsequent confirmed disabled save processes
  remaining pending articles without deciding already completed entries again.
  Requests admitted under an earlier settings snapshot may finish later; the
  bounded sweep is not a cross-collection transaction or a permanent auto-approver.
- Pre-publication requests remain unpublished in the queue until approved,
  including root-owned articles. Post-publication requests are initially public;
  the first accepted report queues the article without necessarily hiding it.
- Every reporter must be authenticated, not the author, and able to read the
  public article. Optional comments are bounded and escaped. One report is
  accepted per reporter/content version; receipts survive counter resets.
  Anonymous mutation uses Hydro's login handoff, not a successful write.
- Reports and review rejections accumulate across title/body versions. Hide
  when reports are strictly greater than the limit; reject further publication/
  submission when rejection count reaches the limit. Approval clears both.
- Only report-review approval grants unchanged-version reporting immunity.
  Actual title/body changes renew eligibility; metadata/comments/stars do not.
- Pending edits remain queued and invalidate old decision tokens. An explicit
  withdrawal cancels the entry but preserves the review hold and its origin.
  Editing, withdrawal/republication and force reset cannot lift the hold; only
  approval can. Disabling review now performs that approval for pending entries.
  Rejected/held articles outside the queue are unchanged and still require
  approval on resubmission. Reset clears counts without publishing or approving.
- Confirmation wording distinguishes direct publication from actual review
  submission. Ordinary publication/live edits in disabled or post-publication
  mode do not mention pre-publication review; held drafts still describe their
  real submission requirement, even when review is disabled.
- `REVIEW` permits queue inspection and decisions without ordinary edit/publish/
  draft-read grants. Reviewers may review their own articles. Authors still need
  existing draft-read permission. Reset has its own independent permission.
- Public responses omit private review data and all pending-write payloads.
  Authors can read their own last rejection; authorized review pages paginate
  independent report history. Own-receipt acknowledgement never reveals hidden
  article content or permits another hidden-article report.
- Report counts require authenticated `ACCESS` and `REVIEW` in HTML and JSON.
  Authorship or reset-only permission is insufficient, including on list/detail/
  editor and counter-reset responses. Authors retain their rejection feedback;
  reset-only users can still reset both counters without reading report counts.
- The first valid article conditional write wins a decision. Stale/repeated
  decisions cannot repeat the count change, approval, decision notice or audit.
  This is database ordering, not a network arrival-order guarantee.
- Report acceptance atomically updates article counters/queue/visibility and
  one bounded pending receipt payload. Idempotent materialization saves the
  independent receipt and clears the slot, advancing the write revision again.
  Foreground operations and native maintenance recover interrupted writes.
  A stale materializer cannot silently adopt a later article mutation.
- `blog.review`, `blog.report`, `blog.review.reset`, and `blog.review.settings`
  record decisions, accepted reports/automatic hiding, resets and configuration.
  Audit data includes the global article identity while retaining native request
  domain/operator context. Oplog is not the report store.
- Authors receive native approval/rejection/threshold-hiding notices. Reviewer
  reminders are separately switchable: login once, then global periodic
  nonzero summaries. Eligible default users, including retired-assignment
  fallback, receive them without a population cap. Administrators control grants.
- Login-reminder failure is explicitly logged without breaking authentication.
  A fixed native maintenance wake-up continues recovery when reminders are off.
  Persisted due/configuration/lease state guards summary occurrences and
  recipient batches; missed periods are coalesced, not replayed.
- Native messages/audit and article persistence are not a transaction. Failures
  can leave committed state or missing/partial notices; summaries are not
  durably retried. Leases do not recall an in-flight native message.
- Deletion extends the native explicit cascade and propagates cleanup failures.
  Late report materializers compensate for parent deletion. There is no global
  orphan sweep or guarantee of zero residual records in every crash window.

## Notification Language

New review decisions, report-hiding notices, automatic-approval notices, reviewer
reminders, comment mentions and deletion notices select their message template
using each recipient's persisted `viewLang`. An unset or empty preference falls
back to `server.language`. The actor's request language is not used.

The shared sender reads only recipient IDs and language preferences in one bulk
query, deduplicates targets and groups delivery by language. Missing accounts and
empty recipient lists do not create messages. Native system-sender identity,
rich-text/unread flags, and awaited error propagation remain unchanged.

Only the template is translated. Usernames, article titles, comments and links
remain separate native rich-message parameters, preserving escaped display and
clickable links rather than interpolating untrusted content into the template.
Existing message records are not rewritten. Multiple language groups can be
partially delivered if a later send fails; there is still no transaction or
notification outbox.

This follows Hydro's recipient-language selection in `MessageModel.sendNotification`,
but uses `MessageModel.send` because the built-in notification helper selects its
own system-privilege recipients and formats a flat string instead of this addon's
explicit recipients and structured link parameters.

## Comments, Replies, and Likes

- Reading comments inherits article reading; there is no separate comment-read
  permission. The native `pagination.reply` setting controls top-level pages
  (Hydro's inspected default is 50), newest first. Nested replies remain in
  insertion order and are not separately paginated.
- `CREATE_COMMENT` permits posting and liking/unliking on both levels.
  Drafts reject all three operations even for root. Withdrawal preserves the
  thread; authorized draft readers can still read and perform permitted deletion.
- Both levels are immutable after posting. There is no edit, raw/history, lock,
  or generic emoji-reaction operation. Replying to a nested reply stays in the
  same top-level thread using the native mention interaction. Existing replies
  never disable subsequent replies or likes.
- Each user has independent like state per target. The `like` operation accepts
  `drid`, optional `drrid`, and required `liked`; explicit false cancels a like.
  Initial unlike and repeated desired states do not change the count again.
  Articles retain stars, not likes.
- Like/unlike rechecks publication after its writes. On rejection it conditionally
  restores only the status transition tagged by that request and reverses its
  count delta only when restoration matched; a newer transition is not overwritten.
- Top-level deletion first allows an article owner with
  `DELETE_COMMENT_IN_OWN_POST`. Otherwise, a self-authored target requires
  `DELETE_COMMENT_OWN`, and another user's target requires `DELETE_COMMENT`.
- Nested deletion allows the reply author with `DELETE_COMMENT_OWN`, or anyone
  with `DELETE_COMMENT`. Own-article moderation does not apply to nested replies.
  Thus global deletion can substitute for own deletion on a nested reply, but
  not on a self-authored top-level comment. This asymmetry intentionally matches
  the inspected official handler.
- Every target operation verifies the full article/comment/nested relationship
  in the system domain. A valid ID from another article is not sufficient.
- Posting invokes the separate `add_blog_comment` limiter with `3600, 60`,
  retaining Hydro's configured limit key, overrides and unlimited-access bypass.
  Both levels share that bucket; article creation uses its existing bucket.
- `nReply` counts top-level comments only. Comment operations never update
  article `updateAt`/`firstPublishAt` or add an activity timestamp.
- Native mention syntax notifies existing, deduplicated targets before saving,
  without a recipient-readability filter. Deletion, applicable moderation
  notification, and `blog.reply.delete`/`blog.tailReply.delete` audit run concurrently.
  Notices preserve the native content excerpt/title/link, adapted to blogs.
  Self-deletion is not notified; deleting a top-level thread notifies only that
  top-level author. Article deletion does not fan out comment notices.
- Creation and likes have no operation-log entries. Notification/audit/data
  writes are not a transaction: a failure can follow a message or partial write.
  Genuine persistence failures propagate; no rollback or exactly-once claim is made.
- Top-level deletion cleans its embedded replies and their likes; nested deletion
  cleans only that target and its likes. Count changes depend on actual removal,
  avoiding duplicate decrements. Shared-collection indexes are comment-scoped.
  Both article deletion helpers remove the article before beginning comment
  cleanup, so new comments cannot validate a still-present parent after cleanup.
